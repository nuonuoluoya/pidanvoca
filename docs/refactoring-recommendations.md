# PidanVoca 项目重构建议

## 1. 结论

当前项目适合继续进行渐进式重构，但不建议直接重写。

词库迁移为 JSON 已经解决了词库格式和按需加载的基础问题。现阶段真正需要处理的是：`build-vocabulary.js` 同时承担页面模板、CSS、运行时代码、依赖内嵌、词库打包、CSP 生成和产物写入等职责，导致源码集中、生成文件庞大，并出现多份相同数据。

重构的核心原则是：

> 不要求单文件离线产物本身看起来简洁，而是让生成它的源码简洁；在线版负责高效加载，离线版负责完整自包含。

项目可以继续保留原生 JavaScript、静态托管和无后端架构，不需要为了重构引入 React 或 Vue。

方案可以执行，但必须将“代码搬迁、引入打包器、改变加载方式、迁移部署和删除重复文件”拆成相互独立的阶段。每个阶段只改变一个主要变量，并在进入下一阶段前完成构建、浏览器、性能和兼容性验收。

## 2. 当前项目分析

### 2.1 体积与代码规模

| 项目                                      |             当前情况 |
| ----------------------------------------- | -------------------: |
| `build-vocabulary.js`                     |  约 259 KB、6,314 行 |
| `dist/web/index.html`                     |           约 1.30 MB |
| `vocabulary-flashcards.html`              | 约 3.81 MB、9,538 行 |
| `dist/offline/vocabulary-flashcards.html` | 约 3.81 MB、9,538 行 |
| 页面内联 CSS                              |            约 326 KB |
| 在线版主运行时脚本                        |            约 643 KB |
| 离线版主运行时脚本                        |           约 2.58 MB |
| 页面脚本块                                |            24～25 个 |
| 7 本内置词库源文件总量                    |           约 3.17 MB |

当前体积预算使用情况：

| 产物      |       实际体积 |           预算 | 已使用 |
| --------- | -------------: | -------------: | -----: |
| 在线 HTML | 1,298,935 字节 | 1,310,720 字节 |  99.1% |
| 离线 HTML | 3,813,406 字节 | 3,932,160 字节 |  97.0% |

在线和离线产物都已经接近现有预算上限，继续直接向 `build-vocabulary.js` 添加功能会很快触发体积门禁。

### 2.2 `build-vocabulary.js` 职责过多

当前构建脚本主要包含：

- 约 2,482 行内联 CSS。
- 约 2,900 行页面运行时代码。
- 完整页面 HTML 模板。
- 20 多个业务模块的读取与内嵌逻辑。
- `ts-fsrs` 浏览器包的内嵌逻辑。
- 在线版和离线版的字符串替换。
- 内置词书和私人词书的构建逻辑。
- CSP 哈希生成。
- Service Worker 源码生成。
- 所有构建产物的文件写入。

这使构建脚本既是构建工具，又是页面源码和应用入口。后续调整样式、DOM 或动画时，都需要在一个数千行模板字符串中修改代码，维护风险较高。

### 2.3 在线版仍然内嵌默认词书

虽然其他内置词书已经通过 JSON 按需加载，但在线版仍将默认四级词书的数据嵌入主运行时脚本。

结果是：

- 在线 HTML 初次加载体积仍接近 1.30 MB。
- 浏览器必须先解析默认词书对象，才能完成应用启动。
- 更换默认词书会导致整个 HTML 和 CSP 哈希发生变化。
- Service Worker 无法独立缓存和版本化默认词书。

在线版应当让所有内置词书，包括默认词书，都经过 manifest 和 JSON 文件加载。

### 2.4 离线版启动时创建全部词条对象

离线版本需要包含全部 20,319 个词条，这是单文件离线能力带来的合理体积成本。

当前问题不在于“包含全部词库”，而在于词库以 JavaScript 对象字面量直接进入主脚本，页面启动时会立即解析并创建全部词条对象。

更合理的方式是：

- 将每本词书作为独立 JSON 字符串或非执行 JSON 数据块嵌入。
- 启动时只读取 manifest 和默认词书。
- 用户切换词书时再执行对应词书的 `JSON.parse`。
- 已解析词书可以按需缓存，避免重复解析。

这样不能显著减少离线文件的磁盘体积，但可以降低首次启动时的 JavaScript 解析成本和对象内存占用。

### 2.5 仓库中存在重复数据

当前 `wordbooks/*.json` 与 `data/books/*.json` 的文件内容及 SHA-256 完全相同，总计重复约 3.17 MB。

同时：

- 根目录 `vocabulary-flashcards.html` 与 `dist/offline/vocabulary-flashcards.html` 完全相同。
- 两份离线文件又重复约 3.81 MB。

仅这两类内容就产生约 6.98 MB 的重复文件，并会持续放大 Git 历史。

建议建立唯一数据源：

- `wordbooks/*.json` 作为内置词库源文件。
- `data/books/` 仅在构建或部署阶段生成。
- 完整离线 HTML 在仓库或发布产物中只保留一份。

但这项清理不能直接执行。当前 GitHub Pages、根目录 `file://` 入口、在线失败回退、README 下载链接和 CI 都依赖这些生成文件。若要让 `data/books/` 不再进入仓库，应先将 GitHub Pages 改为由 GitHub Actions 发布构建 Artifact；若要删除一份离线 HTML，应先确定唯一稳定下载地址并更新全部入口和回退路径。

### 2.6 静态资源内嵌过多

童趣主题的云朵图片目前在构建阶段转换为 Base64 并写入 CSS，是内联 CSS 达到约 326 KB 的主要原因之一。

在线版应直接引用带内容哈希的静态图片；离线版再由构建器将图片转换为 Data URI。

目前还有两个未发现代码引用的资源，可在确认后删除：

- `assets/playful-paper-beach.png`，约 1.06 MB。
- `assets/playful-paper-sun.png`，约 6.4 KB。

实际使用的是 `playful-paper-sun.svg`。

### 2.7 模块化只完成了业务核心层

现有 `src/` 已经拆分出以下边界：

- 经典卡组 Controller 和 Model。
- 记忆曲线 Controller、Session 和核心计算。
- 动画协调器和轨迹计算。
- 词书 Controller 与解析器。
- IndexedDB、Repository 和迁移。
- 导入处理器和 Worker。
- 设置 Controller 和应用事件作用域。

这些模块已经为下一步重构打下良好基础，不应重新实现。

下一阶段应重点拆分仍留在页面运行时中的部分：

- DOM 查询和元素引用。
- 经典卡片渲染。
- 记忆卡片渲染。
- 设置抽屉渲染。
- 词书列表渲染。
- 动画 DOM 适配层。
- 页面启动和功能编排。

## 3. 推荐目标架构

```text
src/
├─ app/
│  ├─ bootstrap.js
│  ├─ application-controller.js
│  ├─ dom-registry.js
│  └─ events.js
├─ views/
│  ├─ classic-deck-view.js
│  ├─ memory-review-view.js
│  ├─ settings-view.js
│  ├─ wordbook-view.js
│  └─ completion-view.js
├─ animations/
│  ├─ animation-coordinator.js
│  ├─ card-transition.js
│  ├─ deck-transition-view.js
│  └─ geometry.js
├─ features/
│  ├─ classic-deck/
│  ├─ memory-review/
│  ├─ settings/
│  └─ wordbooks/
├─ services/
│  ├─ import/
│  └─ storage/
├─ styles/
│  ├─ tokens.css
│  ├─ base.css
│  ├─ layout.css
│  ├─ classic-deck.css
│  ├─ memory-review.css
│  ├─ settings.css
│  ├─ playful-theme.css
│  ├─ animations.css
│  └─ responsive.css
└─ templates/
   └─ app.html

build/
├─ build.js
├─ build-web.js
├─ build-offline.js
├─ build-wordbooks.js
├─ build-service-worker.js
├─ inline-assets.js
└─ csp.js
```

这里的目录结构表示职责边界，不要求每个文件都实现为 class。需要特别避免两种新的集中式依赖：

- `application-controller.js` 不应重新接管所有业务状态，只负责协调 Controller、View 和 Repository。
- `dom-registry.js` 不应成为全页面元素的全局袋子。每个 View 只应获得自己需要的 DOM 元素，并通过有限接口对外工作。

例如，`MemoryReviewView` 可以暴露 `renderCard`、`setProgress`、`onRate` 和 `beginUndoTransition`，但不应直接修改 `MemoryReviewController` 的内部状态；Controller 也不应直接查询或修改 DOM。

构建工具推荐使用轻量的 `esbuild`：

- 支持现有 CommonJS，并可逐步迁移到 ESM。
- 可以合并和压缩 JavaScript。
- 可以处理 CSS 与带哈希的静态资源。
- 支持 tree-shaking。
- 可以生成在线版外部资源，也可以将同一构建结果重新内联到离线 HTML。
- 不要求项目引入前端框架或开发服务器。

不过，不应在提取模板、CSS 和页面运行时的同时引入 esbuild。现有模块多数使用 UMD/IIFE 并挂载到 `window.Pidanvoca*`，可以被打包，但短期内无法充分 tree-shaking。更稳妥的顺序是：先把源码从构建字符串中迁出并保持现有加载方式，再把“引入 esbuild”作为独立阶段。esbuild 版本必须锁定，并为开发构建保留 source map 和 metafile 分析结果。

## 4. 推荐的渐进式重构步骤

### 阶段零：建立重构基准和契约

风险：低，是后续阶段的前置条件。

目标：先明确哪些行为、数据和性能不能退化，再移动代码。

执行内容：

1. 记录当前在线 HTML、离线 HTML、初始总传输体积和压缩后体积。
2. 在浏览器中记录 JavaScript 解析时间、默认词书解析时间、首次可交互时间和初始内存占用。
3. 增加“连续构建两次结果一致”的确定性测试，并固定文件排序、换行和哈希输入。
4. 建立在线 HTTP、离线 HTTP 和 `file://` 三类启动契约。
5. 保存带旧设置、旧词书 ID 和学习进度的 IndexedDB 测试夹具。
6. 记录关键 DOM ID、主题、动画层级、CSP、Service Worker 版本和私人词书排除契约。

阶段零的机器可复现基线保存在 `docs/refactoring-baseline.json`。体积数据由
`npm run metrics:refactor` 重新采集；时间类指标只在相同设备、浏览器版本、冷启动条件和至少五次运行取中位数后比较，避免把单次抖动写成硬门禁。

退出条件：

- 连续构建两次的全部生成文件逐字节一致。
- 默认构建明确排除 `wordbooks/my/`，即使开发机上存在私人词书也不会泄漏。
- IndexedDB v2 结构、全部旧词书 ID 映射和旧设置恢复由固定夹具保护。
- 在线 HTTP、离线 HTTP、`file://` 启动，以及桌面端、移动端关键流程全部通过。
- CSP、Service Worker、稳定词书 ID、可见卡片 DOM 上限和产物预算均保持不变。

### 阶段一：拆分构建器并提取模板、CSS

风险：低。

目标：只移动代码，不改变页面加载方式和运行时行为。

执行内容：

1. 将页面 HTML 主体提取到 `src/templates/app.html`。
2. 按固定顺序拆分 CSS，使用 `src/styles/app.css` 作为唯一逻辑入口。
3. 将词书构建、CSP、Service Worker、资源内联和产物写入迁入 `build/` 下的独立模块。
4. 保留当前 JavaScript 拼接、词库读取和在线/离线生成方式。
5. 校验关键 DOM、CSS 层叠顺序、CSP 和产物入口不变。

完成后，`build-vocabulary.js` 只作为兼容构建入口，不再保存数千行 CSS、HTML 和全部构建细节。

### 阶段二：提取页面运行时入口

风险：中低。

目标：把约 2,900 行页面运行时代码迁出构建模板，但暂不引入新打包器。

执行内容：

1. 新建 `src/app/bootstrap.js`。
2. 将应用启动、Controller 创建和初始数据读取迁入启动模块。
3. 将 Service Worker 注册、主题预加载和页面恢复分别拆分。
4. 按 View 范围获取并验证 DOM，避免建立覆盖全页面的全局元素袋。
5. 构建器读取运行时入口并沿用现有脚本加载顺序。

### 阶段三：先拆分低风险 View

风险：中。

目标：先验证 View 边界和页面编排方式，不触碰高风险切卡动画。

执行内容：

1. 提取 `SettingsView` 和 `WordbookView`。
2. 提取完成面板等低交互 View。
3. 页面编排层只协调 Controller、View 和 Repository。
4. 保持经典、记忆和动画相关 DOM 代码原位，等待打包链路稳定。

每迁移一个 View 就运行对应桌面、移动端和 reduced-motion E2E，不把结构调整和视觉修改放在同一提交中。

### 阶段四：独立引入 esbuild

风险：中。

目标：先让新构建器稳定生成单一应用 bundle，不立即改变资源加载策略。

执行内容：

1. 锁定 esbuild 版本和 Node 版本。
2. 以 `bootstrap.js` 作为显式入口，先输出单一 IIFE bundle。
3. 在线版引用该 bundle，离线版内联同一份 bundle 字节。
4. 开发构建生成 source map 和 metafile，发布构建关闭 source map。
5. 逐步将无副作用叶子模块迁移为 ESM；在此之前不把 tree-shaking 收益作为验收条件。

### 阶段五：迁移经典、记忆与动画 View

风险：高，是整个重构中最需要浏览器回归的一步。

目标：让业务 Controller 不依赖具体 DOM，让动画状态和 DOM 表现拥有明确边界。

推荐迁移顺序：

1. 提取 `ClassicDeckView`。
2. 提取 `MemoryReviewView`。
3. 最后提取 `DeckTransitionView`，并按经典前进、记忆评分、连续撤销的顺序逐种迁移动画。
4. 动画阶段继续由 `AnimationCoordinator` 独占，不新增并行布尔状态。
5. 固定主卡唯一性、层级关系、前进飞出、回切遮挡、内容显隐和无动画模式等 DOM 契约。

每迁移一种动画，都必须分别验证经典/童趣主题、桌面/移动端、正常动画/reduced-motion。卡片位置、透明度、层级和动画完成后的 DOM 清理应使用状态断言，而不是只依赖截图。

### 阶段六：建立正式的在线构建

风险：中。

目标：在线 HTML 不再承载完整应用代码和词书，并为新增异步加载提供完整状态处理。

建议输出：

```text
dist/web/
├─ index.html
├─ service-worker.js
├─ assets/
│  ├─ app.[hash].js
│  ├─ app.[hash].css
│  ├─ import-worker.[hash].js
│  └─ playful-*.[hash].png
└─ data/
   ├─ books.manifest.json
   └─ books/*.json
```

执行内容：

1. JavaScript、CSS、图片和导入 Worker 改为外部哈希资源。
2. 默认四级词书也通过 manifest 和 JSON 加载。
3. 为应用壳和词书请求补充加载中、失败、重试和超时状态。
4. Service Worker 原子预缓存应用壳、默认词书和必要代码，避免新旧 HTML 与资源版本混用。
5. 保留必要的主题预加载，避免首次渲染闪烁。
6. 重新审查 CSP；不能仅以“更简单”为理由无条件扩大为信任全部同源脚本。

在线 `index.html` 可将约 50 KB 作为结构参考，但主要验收指标应是初次总传输体积、压缩体积、首次可交互时间、重复访问缓存命中率和失败恢复能力。

### 阶段七：重建单文件离线产物并延迟解析词书

风险：中。

目标：使用在线版相同源码生成完整离线文件，不维护第二套运行时。

执行内容：

1. 离线构建器内联阶段四生成的同一份 JavaScript、CSS、模板和图片资源。
2. 每本词书以独立的非执行 JSON 数据块保存，启动时只解析当前词书。
3. 保持 JSON 中 `<` 字符转义，避免 `</script>` 等内容破坏数据块边界。
4. 已解析词书按需缓存，并允许释放不再需要的原始数据节点或对象缓存。
5. Worker 源码通过 Blob URL 创建。
6. 保持 `file://`、IndexedDB 回退、语音和词典链接兼容。
7. 重新生成并验证离线 CSP 哈希。

离线文件仍会有数 MB；这一阶段主要降低 JavaScript 解析和词条对象内存，不承诺显著缩小磁盘体积。

首版缓存使用简单的 `Map`，只缓存真正打开过的词书。除非真实长会话内存测量证明有必要，否则不提前引入 LRU 和复杂淘汰策略。

### 阶段八：部署迁移和重复文件清理

风险：中高，需要部署方案先行。

执行内容：

1. 决定继续从仓库分支发布，还是改为 GitHub Actions Pages Artifact。
2. 只有改为构建 Artifact 后，才让 `data/books/` 退出 Git 跟踪。
3. 确定唯一离线下载地址，再更新根入口、在线失败回退、README 和 E2E。
4. 保留 `wordbooks/*.json` 作为唯一词库源。
5. 确认构建和引用检查通过后删除无引用图片。
6. 更新发布与回滚文档，保留上一版本构建 Artifact。

推荐使用 GitHub Pages Artifact 作为唯一发布目标，并用可回退的 Git 标签标记每次发布。仓库中的源文件和部署产物职责分离后，再清理重复生成文件。

### 阶段九：ESM 化和移除兼容层

风险：中，应在 View、构建和部署都稳定后执行。

执行内容：

1. 从无副作用叶子模块开始迁移为 ESM。
2. 分阶段移除 `window.Pidanvoca*` 和旧变量兼容绑定。
3. 每删除一层兼容绑定，都验证没有浏览器、测试、旧数据迁移或外部入口仍在使用。
4. 最后再评估在线记忆曲线代码分割是否有足够收益。

不要在同一提交中同时删除所有兼容层，也不要把代码分割作为默认目标。应先测量模块体积和首次打开记忆模式的延迟，再决定是否动态加载。

## 5. 性能优化建议

### 5.1 在线词书全部按需加载

- 首屏只请求 manifest 和默认词书。
- 切换词书时按 ID 请求 JSON。
- 使用内容 hash 作为缓存版本。
- 缓存最近使用的词书，避免反复解析。

### 5.2 离线词书延迟解析

- 文件仍包含全部词书。
- 首次启动只解析当前词书。
- 其他词书保留为 JSON 字符串。
- 切换时再解析目标词书。

### 5.3 将延迟加载记忆曲线作为可选优化

经典模式首次启动不需要立即初始化 FSRS、ReviewRepository 和完整记忆视图。

但动态加载会让第一次打开记忆模式出现新的等待和失败路径，也会让在线、Service Worker 和单文件离线版使用不同的分包策略。应先完成资源外部化并测量记忆模块体积；只有收益明显时才实施。若实施，Service Worker 必须预缓存代码块，界面必须提供加载、失败和重试状态，离线版仍应打包为单一可执行脚本。

### 5.4 保持有限卡片 DOM

现有项目已经将可见卡片 DOM 控制在 7 张以内，这一策略应保留。

词书数量增加不会直接导致切卡动画卡顿；更值得优化的是：

- 首次 JSON 解析。
- 洗牌时的临时数组分配。
- 词书切换时的对象复制。
- 页面启动时不必要的 Repository 和 FSRS 初始化。

### 5.5 静态资源区分在线和离线策略

- 在线版使用外部哈希文件，便于缓存。
- 离线版使用 Data URI，保证单文件运行。
- 不要让在线版为了复用离线构建策略而继续承受 Base64 体积。

### 5.6 使用真实浏览器指标验收

文件从 HTML 移到外部 JS、CSS 或 JSON 后，HTML 会明显变小，但首次访问仍然需要下载和解析这些资源。因此性能验收不能只看 `index.html`：

- 记录首次访问和重复访问的总传输体积。
- 同时记录原始体积和 gzip/Brotli 后体积。
- 记录首次可交互时间、默认词书解析耗时和峰值内存。
- 记录第一次打开记忆模式、切换词书和离线启动的延迟。
- 保留 7 张以内的可见卡片 DOM 预算。

## 6. 安全与兼容性要求

重构过程中必须保留：

- 在线和离线 CSP。
- `script-src-attr 'none'`。
- `object-src 'none'`、Worker 限制和 `no-referrer`。
- 导入内容只通过文本节点渲染。
- 词库 JSON 中 `<` 字符转义。
- 在线词书和 manifest 的 Schema、稳定 ID、词条数量、字段长度及版本校验。
- IndexedDB 数据库版本和迁移顺序。
- 旧词书 ID 映射。
- 旧设置与学习数量迁移。
- “我的单词本”默认不进入构建产物。
- `wordbooks/my/` 的 Git 忽略规则。
- `file://` 离线启动能力。
- reduced-motion 行为。
- 经典模式与记忆模式共享的动画状态机。

在线脚本外部化后需要重新审查 CSP 信任边界。当前内联哈希只允许构建时确认的脚本，而 `script-src 'self'` 会信任同源下所有脚本。静态托管下可以使用 `'self'`，但应配合内容哈希文件名、不可变缓存，并在可行时为入口资源增加 SRI；不得为了打包或 source map 引入 `unsafe-eval`。

Service Worker 更新必须保证 HTML、应用 bundle、manifest 和默认词书属于同一版本。不能在用户当前学习过程中强制激活，也不能让旧 HTML 长期引用已经删除的新哈希资源。

## 7. 测试与验收标准

每个阶段完成后应执行：

```bash
npm run check
npm run perf:check
npm run test:e2e
```

建议增加以下构建契约：

1. 在线 HTML 不包含完整词条数组。
2. 在线 HTML 不包含 Base64 主题 PNG。
3. 在线默认词书通过网络 JSON 请求加载。
4. 离线文件通过 `file://` 启动且不发起核心网络请求。
5. 离线文件包含全部 7 本内置词书。
6. 默认构建不包含 `wordbooks/my/` 的文件名和内容。
7. 在线和离线使用同一应用版本和 Schema。
8. 构建结果具有确定性。
9. Service Worker 缓存版本随资源内容变化。
10. 生成页面不存在重复的模块或事件监听器。
11. 连续构建两次得到相同 manifest、资源哈希和产物内容。
12. 旧设置、旧词书 ID 和既有 IndexedDB 学习进度可以无损恢复。
13. 在线词书加载失败时能够重试，且不会破坏当前词书和学习进度。
14. CSS 拆分后经典、童趣、桌面、移动端和 reduced-motion 的关键样式保持一致。

最终验收目标：

- 现有 88 项单元测试保持通过。
- 现有 52 项浏览器用例保持通过或由等价的新用例替代。
- 在线版不再内嵌任何完整词书。
- 在线 `index.html` 以约 50 KB 作为结构参考，而不是唯一性能门禁。
- 首次总传输、首次可交互、词书解析和内存指标不劣于阶段零基准。
- 离线版仍可单文件独立运行。
- “我的单词本”只保存在浏览器本地或被 Git 忽略的私人目录。
- 若已迁移到构建 Artifact 发布，仓库不再保存两份相同词库和两份相同离线页面。
- 经典模式与记忆模式动画效果不退化。
- IndexedDB 中的现有学习进度能够无损恢复。
- CSP、Service Worker 和无障碍行为不退化。

## 9. 重构的缺点与代价

- 重构期间新功能开发速度会下降，一段时间内还会同时存在旧入口和新模块，短期复杂度会上升。
- CSS 拆分可能因为顺序变化造成细微视觉差异，动画 DOM 拆分则可能重新引入闪烁、透明度、层级和卡顿问题。
- 外部资源会增加网络请求、加载状态、失败重试和缓存版本不一致等新问题。
- Service Worker 与哈希资源组合如果更新不原子，可能出现新 HTML 引用旧资源或旧 HTML 引用已删除资源。
- esbuild 增加工具链和供应链依赖，生产代码位置也不再直接对应源文件，需要 source map 和构建分析辅助调试。
- 延迟加载只减少首次解析，不减少最终需要下载的总资源；第一次打开记忆模式反而可能更慢。
- 离线词书延迟解析能减少词条对象，但 HTML 仍需持有原始 JSON 文本，内存收益不会与文件体积成正比。
- 删除生成文件后，发布会更加依赖 GitHub Actions；构建或 Actions 故障时不能直接使用仓库中的现成产物发布。
- 对当前规模的原生项目，过度拆分类和接口可能让简单修改横跨过多文件；必须以清晰状态所有权和真实复用需求作为拆分依据。
- 单文件离线版最终仍会保持数 MB。重构主要改善源码维护、浏览器解析和缓存，不会让完整离线文件显著变小。

## 10. 建议的实施方式

继续采用渐进式、小提交重构：

1. 每个提交只处理一个明确边界。
2. 不在同一提交中同时改变结构、动画和视觉样式。
3. 每次提交前重新构建在线和离线产物。
4. 每个阶段完成后保留可回滚标签或稳定提交。
5. 先迁移代码，再删除兼容代码。
6. 先建立测试契约，再改变构建格式。
7. 一个提交不要同时引入 esbuild、迁移模块格式和改变资源加载方式。
8. 在线和离线产物始终从同一应用 bundle 生成，避免形成两套运行时。
9. 部署迁移完成前，不删除当前 Pages、下载和 `file://` 入口仍依赖的文件。

建议先实施阶段零、阶段一和阶段二。它们可以建立可量化基准并显著缩小 `build-vocabulary.js`，又不会立即引入打包器、改变词库读取、部署或离线运行方式，是收益最高且最容易回滚的起点。
